The constraint

One instance per trainee is not a preference. It is the whole problem.

Partner training servers today take one or two logins, and two trainees working at once on a single Xill4 instance get in each other's way. So the sandbox cannot be one Xill4 with many users. It has to be N isolated instances, provisioned and reclaimed on demand.

That is the hard part, and it is the part whose answer we don't have yet. Grading, progression and reporting are comparatively easy — and they should not be tangled up with it. So they aren't: the grading layer already runs, today, with no Xill4 anywhere near it.

The mechanism

The answer key lives where the trainee cannot reach it

A workspace is three directories on the host. Two are mounted into the trainee's Xill4 instance. The third — the answer key generated from that trainee's own seed — is mounted nowhere. The grader runs on the host side and reads all three.

That asymmetry is the entire isolation mechanism for grading. No secrets in the trainee's reach, nothing obfuscated, nothing to leak.

Provisioning

Build against containers, keep VMs as the fallback

Provisioning sits behind one interface: give me an isolated Xill4 with these volumes mounted, and tell me how to reach it. Three implementations are plausible, and the economics differ by an order of magnitude.

BackendFits whenCost per traineeResetStatus
Container per trainee Xill4 can run headless on Linux A slice of one shared host seconds Target state
VM per trainee Xill4 only installs onto a full OS A whole VM, always minutes Works today — safe fallback
Pooled desktop Trainees need the Xill IDE, not just the engine An AVD session host slice minutes Only if the IDE is required

Ten containers on one host, reset in seconds, is a different product from ten VMs redeployed one at a time. That is why it's worth asking the question before Phase 1 starts. But note what does not change with the answer: not one scenario, not one check, not one line of the grader.

Grading

Four decisions, each buying something specific

Grade outcomes, not keystrokes

A check asserts on what ended up in the target system, never on which Xill4 constructs the trainee used. Two trainees can solve a scenario differently and both score 100. This is what makes the sandbox teach migration rather than button order — and it means scenarios survive Xill4 UI changes.

Seed per trainee

Every workspace is generated from hash(trainee, scenario). Trainees get structurally identical, textually different data: the same kinds of dirty record in different rows. So expected values are not constants in the scenario file — a check references a fact about the trainee's own seed, equals: {from: facts.json, query: files_on_share}. One scenario, N answer keys, and a copied answer scores zero.

Fail loudly, never silently pass

An unknown check type, a check that raises, a missing workspace variable — each fails the task or aborts the run with a named error. The one thing a grader must never do is award points because it couldn't tell.

Every scenario ships a reference solution, and CI runs it

Two invariants are asserted for every scenario on every commit: the reference solution scores 100/100, and an untouched workspace scores 0/100 with every task failing. A suite that only satisfies the first grades nothing. Both together are what make a scenario safe to put in front of a paying partner.

Over to you

What I need from Xillio

None of these block starting. The first two decide what Phase 1 looks like.

Can Xill4 run as a container? Blocks phase 1

Is there a Linux image, or can the engine be installed headless into one — and does the licence permit N short-lived instances rather than N named servers? Yes means a container per trainee and resets in seconds. No means a VM per trainee, which costs more and works fine.

Do trainees need the Xill IDE, or only the server? Blocks phase 1

Server-only keeps everything browser-reachable and the container path open. If the desktop IDE is required, a workspace becomes an Azure Virtual Desktop session and the grader runs beside it instead of against a mounted volume. The scenarios are unaffected either way.

Does Xill4 expose an API for project and job state? Improves feedback

If it does, checks can assert on the migration itself, not only its output — the job completed without errors, the pipeline contains a transformation step, the run processed N records. That makes feedback like “your job ran, but it skipped the archived records silently” possible.

Which existing exercises become scenarios 02 and up? Curriculum

Scenario 01 was written from first principles to prove the loop. The real curriculum should come from the exercises already used in the programme. Porting one is mostly writing its seed generator and its checks — a day or two each.

Where does the capstone run? Curriculum

Stand-ins grade better; a real tenant teaches the lesson about a real system's friction. The proposal is stand-ins throughout and a real tenant at the end — but which system that capstone targets is your call.
