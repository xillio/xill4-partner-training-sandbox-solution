Problem

We don’t own the environment the training runs on

Today trainees work in an environment the partner provides. Five consequences follow:

  • No control — what is installed, what data exists, when it is available
  • Exercises can’t be designed in advance — the data isn’t ours
  • Pacing depends on someone else’s IT — training stalls when the environment isn’t ready
  • No two partners get the same training — so outcomes vary by partner, not by engineer
  • Hands-on work can’t be verified automatically — we don’t know what “correct” looks like in their environment

Proposal

A sandbox Xillio owns, with exercises Xillio authors

  • One isolated Xill4 instance per trainee — reached in a browser, no partner setup
  • An exercise per topic — controlled scope, defined outcome, realistic messy data
  • Automatic verification — scored in seconds, with the specific wrong value named
  • Progress recorded per trainee, per topic — not one pass/fail at the end
  • Partner picks the source and target systems — practice matches the migration they were contracted to deliver

Because Xillio authors the extraction scope, the transformation rules and the target structure, the correct outcome is known before the trainee starts. That is what makes automatic verification possible — and why it cannot be done in an environment the partner provides.

Precedent: the practical Xill4 exam is already marked automatically. This extends that from one exam at the end to every topic along the way.

Delivery

How the training itself changes

  • Long workshops become short stand-ups — next tasks, review the last one, deadlines per trainee
  • Deadline per exercise, per trainee — a miss means nothing was submitted, never a failed attempt
  • One grace deferral per course — stated in the joining terms, not discovered at enforcement
  • Two misses: automatic notice — to the trainee and the partner contact. Third: the trainer decides.
  • The cohort is never held back — a trainee who falls behind finishes self-paced within a fixed window after the end date
  • Sandboxes outlive the cohort — through that window, with a hard expiry; the trainer is not on support during it

Self-paced completion is only offerable because marking is automatic. It is a consequence of the sandbox, not a policy beside it.

Phases

Four phases, each with a gate

Phase 1

One sandbox, and a measured pilot

  • Provision a Xill4 container per trainee, seed the data, run one exercise end to end with a real person
  • Needs — registry token, training licence key, a host, new Harvest project
  • Gate — target hours met, and the trainee judges the marking fair
Phase 2

Cohort-ready

  • Provisioning for a full cohort, sign-in for external trainees, both dashboards, automated notices
  • Gate — first cohort delivered on the sandbox; Harvest shows the hours falling
Phase 3

Exercise library

  • One exercise per topic, so stand-ups can replace workshops. Progression unlocks as trainees pass.
  • Needs — a day or two per exercise from whoever owns the material
Phase 4

Self-service enrolment

  • Partners enrol when they need to; more source and target systems added as demand appears

Systems

Which systems trainees practise against

A source is read, a target is written — so a cohort shares one source, but each trainee needs their own target space.

Each system needs one adapter, built once, then usable by every exercise — so a menu of combinations does not mean a matrix of exercises. Trainees can see each other’s folders harmlessly: each has different seed data, so a copied migration scores zero.

Both ends of OpenText Content Server → SharePoint Online are already available to us — the OTCS demo VM as a shared read-only source, SharePoint Online as the target. That is the migration partners most often have to deliver, and it can be the first realistic end-to-end exercise.

Dashboards

Two dashboards, split on a trust boundary

Internal — PO and trainer

  • All cohorts; progress per trainee, per topic
  • Attention list: stuck vs silent — different problems
  • Which exercise a whole cohort fails — the material, not the trainees
  • Trainer hours per cohort, as a trend — from Harvest
  • Cohorts per quarter, completion, capacity

External — trainee and partner

  • Trainee sees only their own progress and deadlines
  • Partner contact sees only their own engineers
  • Never hours, never cost, never other trainees
  • Completion evidence per topic, generated

Trainees are external, so this is a security boundary rather than a layout choice.

Proof

How we will know whether it worked

  • A new Harvest project is a requirement of running the pilot — not a recommendation
  • Its tasks roll up to today’s categories — so the pilot compares against real past cohorts, not a blank page
  • Baseline fixed before the pilot starts — from cohorts already logged
  • The pilot passes only if both hold — the hour target is met, and a real trainee judges the marking fair

The request is therefore self-auditing: approval rests on a claimed reduction, and Harvest settles it by the third or fourth cohort.

Risks

Risks

  • Container resource use is unknown — fewer sandboxes per host would raise Phase 2 hosting. Phase 1 measures it first.
  • Exercise authoring is the real ongoing cost — infrastructure is cheap; curriculum is the investment. Plan for it.
  • Trainee work lives in MongoDB — keeping or resetting it is a database design task, not an afterthought.
  • Live cloud targets can fail correct work — jobs queue and throttle. Stand-ins teach technique; real services only where their friction is the lesson.
  • Licence terms per instance — expected fine for training-only use, worth confirming in writing before Phase 2.
